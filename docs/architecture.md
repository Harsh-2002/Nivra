# Architecture

Nivra has a Next.js application shell, client-only BlockNote/Excalidraw editors, and authenticated Node.js route handlers. Workspace sections have direct URLs: `/overview`, `/notes`, `/favorites`, `/journal`, `/tasks`, `/calendar`, `/bookmarks`, `/artifacts`, `/forms`, `/tag-suggestions` and `/trash`. Search and Settings use `/search` and `/settings` on mobile. The root opens Overview. Client navigation updates browser history while retaining the workspace shell and editor save guard; direct loads select the section from the path. Unknown sections return 404. Every private route requires authentication. PWA navigation remains network-only.

SQLite is the only database. Drizzle defines the schema and handles model/auth mapping; prepared SQL handles FTS5, transactional updates, and ordered startup migrations. Each connection targets a 32 MiB SQLite page cache to avoid repeatedly decrypting pages during larger searches. This is a cache target, not a process memory limit.

## HTTP contract

`/api/v1` routes are matched against the operation registry in `api-contract.ts`. Its shared Zod request/response schemas generate [OpenAPI](openapi.json); `npm run verify:api` checks generated-contract drift and validates the specification and references. The contract is available in the repository only; the instance does not serve an OpenAPI discovery endpoint. HTTP responses are checked at runtime. Content and calendar services accept structured commands; HTTP and MCP share these services without simulated browser requests. Transfer services preserve lossless bundle behavior. Account and instance operations require the owner session; bearer API keys authorize only scoped content access. `/health` is public readiness, and OAuth stays at `/mcp`.

## Data and saves

Notes store a versioned BlockNote JSON document. Plain text derived from the blocks feeds FTS5. Every update includes an expected revision; a mismatch returns HTTP 409. The editor serializes saves and preserves newer local edits while a request is in flight. A failed request keeps edits in memory and warns before page unload. This release does not store offline drafts.

Canvas blocks store scene JSON and refer to local attachments for their embedded images and preview. Markdown exports contain portable text, Mermaid fences, local attachments, and drawing sidecars; some rich formatting is simplified. Versioned Nivra bundles preserve document JSON and files, import as new notes, and remap attachment identifiers.

## Accounts and access

The onboarding wizard creates one owner with a name, username or email identifier, and either a password or verified passkey. Identity, sign-in method and encryption are separate guided steps. No setup request is sent before the encryption choice; account creation then remains atomic. Recovery-code saving and optional storage configuration follow. A SQLite trigger and setup transaction enforce the single-owner invariant. Better Auth manages password hashes, sessions, optional TOTP and discoverable passkeys; username-only identifiers receive an internal `nivra.invalid` address without requiring mail infrastructure. Public signup is disabled. Authentication configuration is reused in a bounded origin cache; sessions are still checked against SQLite, so revocation remains immediate.

A one-use recovery code is hashed in the database. Recovery changes the credential password, revokes all sessions, and replaces the code in one transaction. Generating a replacement requires the current password, or a fresh passkey session when no password exists. Recovery and setup have bounded attempt limits.

Application HTML uses a fresh script nonce and dynamic rendering. The proxy overwrites incoming nonce headers, and production disallows script evaluation and unapproved inline scripts. Editor, drawing and positioned-control styles use nonce-authorized stylesheets; inline style attributes are blocked. Published HTML retains its separate reader policy. Responses deny framing, restrict cross-origin access and browser permissions while allowing same-origin passkeys and clipboard actions, and enable HSTS when the canonical public URL is HTTPS. Cross-origin embedder isolation uses `require-corp`; validated remote media is served through bounded same-origin routes.

[MCP](mcp.md) exposes `/mcp` through the official TypeScript MCP SDK. OAuth uses Better Auth with verified client metadata, PKCE, owner consent and resource-bound tokens; local agents can use hashed API keys. A shared content dispatcher applies the same ownership, validation, revisions, storage and durable job behavior as the browser. Agent permissions exclude account and server administration. SQLite stores credential revocation and retry state; agent changes publish browser SSE invalidations.

## Files and runtime

The data directory contains `nivra.sqlite`, SQLite WAL files, `auth.secret`, and `uploads/`. Attachments have generated identifiers and are served only through authenticated routes. Raster image types are detected from their signatures. An allowlist of raster and audio/video types is served inline; active formats and unrecognized types download as binary files. Private and token-scoped published attachments support single byte ranges for media seeking, with no-store caching, sandboxed responses, and nosniff headers. By default, stored files are encrypted in independently authenticated chunks, so a range request reads, authenticates and decrypts only the chunks it covers, and larger responses are streamed a megabyte at a time. Encrypted reads allocate one owned plaintext result and read ciphertext in batches of at most 1 MiB for the standard chunk format. Artifact workers receive that buffer through an ownership transfer rather than a cloned file. Legacy migration retains a separate reader buffer, preventing worker transfer from detaching migration data. S3 servers that ignore Range require a full-object response; that response is reused instead of downloaded once per batch. The storage adapter supports local files or an S3-compatible bucket configured in Settings → System. The modular AWS SDK signs object reads, writes, and deletes; credentials remain server-only. SQLite stays local with either file backend.

The PWA caches public static assets and an offline explanation. Notes, API responses, and attachments are network-only. Fonts and drawing assets are bundled with the application.

## Deferred work

IndexedDB offline editing and synchronization, Yjs collaboration, shared workspaces, and executable HTML/React previews are not available in this release.

## Dependency maintenance

Direct dependency versions and the lockfile are pinned. `npm audit --omit=dev` currently reports no advisories. The development lint toolchain has an unresolved `braces` denial-of-service advisory inherited through `eslint-config-next` and `fast-glob`; npm's proposed fix downgrades the Next.js lint configuration across major versions. Do not apply that downgrade blindly. Keep lint inputs limited to trusted project files and revisit when an upstream compatible fix ships.

The viewport and single scrolling wrapper follow [BlockNote's mobile keyboard guidance](https://www.blocknotejs.org/docs/react/components/formatting-toolbar#browser-limitations). The workspace inherits the visual viewport height so the editing area remains above the keyboard.

## Publication snapshots

Publishing checks the expected note revision, copies only referenced note-owned attachments, rewrites their URLs to token-scoped public endpoints, and commits the snapshot and file records together. Private drawing scene data is omitted; readers see its preview. Public APIs return no owner, private note IDs, tags, or draft revisions. Later private edits do not change a publication. Updates preserve its link; revocation deletes the publication and its copies, and a subsequent publication gets a new token. Trashing a note revokes it. Public pages and files are network-only with no persistent service-worker caching.

## Overview

The default Overview reads an authenticated, owner-filtered snapshot from `GET /api/v1/overview?date=YYYY-MM-DD`. The supplied date is validated and comes from the browser’s local calendar, so due-today and overdue counts follow the owner’s device rather than the server timezone. Drizzle queries inside one SQLite read transaction count all open tasks and return bounded lists of twenty tasks, twenty recently edited active notes, and twenty recent bookmarks. Templates and trashed notes are excluded; document bodies and attachment data are not included.

Overview uses independent, content-driven cards for open tasks, upcoming events, recent notes and files, recent bookmarks, recent form submissions, and items needing review. Empty categories are omitted. Cards use bounded quick-glance lists and the page scrolls naturally as more categories appear; desktop cards do not force their lists into nested scrolling areas. Recent form submissions are owner-session-only metadata (form title, submission time and reviewed status), with a direct link to the private response; answers and uploaded files are excluded. Agent/API-key snapshots omit these response summaries and review counts. The additive `recentContent` field separates notes/files from bookmarks while preserving the existing `recentItems` contract.

The client refreshes on mount, shared completion/resync events, window focus and inline task completion. The shared stream reconciles when disconnected; hidden tabs close the stream and suspend the minute-aligned local clock timer. Unmount aborts outstanding snapshot requests. Task mutations use existing expected-revision checks and recurrence transactions. Overview reuses guarded workspace navigation and existing creation flows; it introduces no database tables, persistent preferences, event stream, or dependencies.

## Search and tags

FTS5 covers note titles, prose, code, and drawing text, with prefix matching and relevance ordering. If the normal query finds no notes, a vocabulary-based fallback finds close spellings (one edit for words of at least four characters, two for words of at least eight, including adjacent transpositions). Short words and exact matches retain their normal behavior. Up to eight terms participate in typo correction. Favorites, tag, and trash filters apply to both paths. Artifacts provide bounded document extraction and local English image OCR; media transcription remains deferred.

Tags cover notes, journal entries, tasks, bookmarks and artifacts through indexed join tables. Owner-authorized tag saves use revision checks; Trash retains relationships and permanent deletion cascades them. Recurring successors inherit task tags. Tags have a validated named color, defaulting to gray. Bundles retain colors for newly imported tags; a same-named existing tag keeps its local color. Tag colors are content metadata, while the interface remains monochrome.

Better Auth's passkey plugin supports optional discoverable FIDO2 credentials, including security keys, device authenticators and password managers. Registration and login require server-verified PIN or biometric verification. The canonical public URL supplies the relying-party ID and origin. Adding, renaming and removing keys require a session created within five minutes. Verified passkey login is sufficient when TOTP is enabled; password login still requires TOTP. Account recovery preserves registered passkeys and revokes sessions; unwanted credentials must be removed explicitly. Passkey records are included in full-instance encrypted backups.

Better Auth's TOTP plugin stores encrypted secrets and backup-code data in SQLite. Enrollment must be verified before activation. Password-only sign-in has no private-note session when MFA is enabled. Single-use account recovery also clears MFA and outstanding verification challenges.

## Tasks

Tasks use a dedicated SQLite table and Drizzle queries scoped to the authenticated owner. Create, update, complete, reopen, and delete requests require the owner session and same-origin writes. Updates and deletion use revision checks. Tasks are separate from BlockNote checklist blocks and participate in lossless bundle export/import.

## Default-on encryption at rest

The better-sqlite3 import is pinned to the SQLite3 Multiple Ciphers fork through an npm alias, preserving the Drizzle driver API. SQLite pages and WAL are encrypted with ChaCha20-Poly1305; temporary SQL storage stays in memory. A random 256-bit master key derives separate SQLite and file keys with HKDF-SHA256. The authentication secret, backup manifests and backup objects use one AES-256-GCM message with a random nonce and an authenticated object identifier (the single-message v1 format). Attachments and other stored files use the chunked v2 format. Local and S3 adapters encrypt before writing and authenticate before returning plaintext.

Onboarding chooses the encryption mode before database initialization. The owner-only `encryption-mode.json` record persists the choice and cannot be changed afterward. Complete records are atomically published without overwriting a concurrent startup's decision. Missing keys, incorrect keys and authentication failures never fall back to plaintext. When encryption is disabled, SQLite and files use plaintext storage; authentication secrets and backups remain encrypted.

## Bookmarks

Bookmarks use an owner-scoped Drizzle model with expected revisions, unique normalized URLs, collections, favorites, and an independent FTS5 index/vocabulary. Search matches title, description, URL and collection, with prefix, substring and close-spelling fallback. URL saves fetch Open Graph/Twitter/HTML metadata; unavailable metadata leaves a saved fallback link. Editing is independent of fetching, and preview refresh preserves existing data on fetch failure. Lossless bundles include bookmark details and cached preview assets; importing skips existing URLs.

The metadata fetcher validates HTTP(S), rejects credentials and nonstandard ports, resolves and validates every DNS address, and pins the chosen address for the connection. Redirects and image fetches repeat this check. Private, loopback, reserved, mapped and transition addresses are blocked. A shared ten-second deadline, three-redirect limit, 1 MiB HTML limit and 2 MiB image limit bound requests. An inert parse5 HTML tree supplies metadata and decodes entities once; comments, script/style text and template content cannot create metadata elements. Extracted labels remain plain text, and asset URLs pass HTTP(S) validation. Script execution and headless browsing are not used. Cached raster previews use generated storage IDs and the installation's saved encryption mode; the browser only requests owner-authorized Nivra image routes. Unsupported image formats use a fallback rather than rendering active source content.

## Encrypted recovery backups

Local storage is the default; hybrid storage puts files in ordinary S3-compatible objects while SQLite remains local. Backups have an independent local/S3 destination, interval and retention policy. The default is a local backup every 24 hours with seven completed copies. The single-instance scheduler checks due work each minute and does not run during production builds. Manual backups use the same implementation. A filesystem lease coordinates CLI and server creation; process-local file pins defer deletions while a snapshot is being copied.

`VACUUM INTO` produces a consistent database snapshot in the installation's persisted mode, which is reopened with the appropriate key or plaintext configuration and checked. Its referenced-file inventory includes attachments, publication files, bookmark thumbnails and icons. Database, encrypted authentication secret, individual file contents and manifest are sealed separately with backup/object-bound AES-GCM. The authenticated manifest records the storage encryption mode and is the final completion marker. Failed copies lack a committed manifest; retention removes the marker first and deletes only backup-owned object names. Abandoned sets older than 24 hours are cleaned after a successful backup. Backup metadata/status is encrypted locally; API responses exclude credentials and filesystem paths.

Restore authenticates the manifest and each object, checks lengths and SHA-256 hashes, verifies SQLite/foreign-key/FTS integrity and the exact file inventory, and materializes a local installation in the backed-up encryption mode in a private staging directory. Older manifests without a mode field mean encrypted storage. Only a new or empty destination can receive it, after full verification. The original key must be supplied independently; backup objects never contain it. A successful local restore contains an owner-only copy of that key for the default local setup. This offline CLI operation does not overwrite or switch the running instance. Recovery verification exercises the same restore path in a disposable directory. The production image contains a small bundled Node CLI without a TypeScript runtime or compiler.

Backups read one complete database/file object at a time in memory, not an entire archive; provision RAM for the largest object and disk space for the database snapshot or verification staging. Backup schedules are periodic recovery points, not continuous replication. Run one Nivra process per data directory; horizontal replicas and distributed file-deletion leases are not supported.

### Backup and recovery commands

Create and verify an instance backup in **Settings → System** and retain the original encryption key separately. Local backups share the server’s failure risk; use S3 or a separately mounted backup directory for host-failure recovery.

With Node.js 24, the recovery CLI supports:

```sh
npm run backup -- create
npm run backup -- list
npm run backup -- verify BACKUP_ID
NIVRA_ENCRYPTION_KEY_FILE=/safe/original.key npm run backup -- restore BACKUP_ID /srv/nivra-restored
```

If the original database is unavailable, append `--backup-directory /safe/backups` for local recovery, or `--connection-file /safe/s3.json` for S3. The private JSON file contains `provider`, `endpoint`, `region`, `bucket`, `accessKeyId`, `secretAccessKey` and `pathStyle`, matching your saved connection. Keep it readable only by its owner.

Restoration requires an empty destination and restores files locally. Content import/export bundles are separate from full-instance recovery. Keep keys, connection credentials and recovery codes outside Git.

## Connected workspace

Migration 0008 adds note checkpoints, stable directed links, template/daily identity, task scheduling, and task FTS5 with triggers and existing-title backfill. Existing notes remain regular notes and existing tasks retain undated, nonrecurring behavior. A partial unique index enforces one daily note per owner/date; the parent-occurrence index prevents duplicate recurring successors.

The authenticated unified-search endpoint parses type/tag filters, applies bounded FTS5 prefix matching across content types, and tries vocabulary typo matching only when no exact results exist. Small match sets use direct row-ID lookups; broad matches use recent-item indexes. Context extraction is limited to the selected row range. Calendar link search uses prefix matching and returns at most ten compact results without snippets, typo expansion or event results. Both modes exclude templates and trashed content. Internal Markdown-compatible links store stable note IDs; saving or restoring a document rebuilds its outgoing edges transactionally. Rename does not invalidate links. Optional task/bookmark foreign keys use SET NULL on permanent note deletion.

Exact counts use partial covering indexes. API/MCP search and collection pages choose identifiers before loading the selected excerpts; broad and selective FTS matches use different query plans. Bookmark search combines word-prefix matches with a case-preserving trigram index over SQLite's existing literal-substring expression; queries shorter than three Unicode characters retain the scan fallback. Artifact context is extracted through one bounded FTS cursor. Typo expansion uses a transactionally maintained term dictionary and FTS5 character-pair index before edit-distance checks, retaining only six matches and a bounded result cache. Per-document term counts use the existing tokenizers, so updates and removals stay exact. Only indexed content changes invalidate that cache. Calendar activity uses indexed date ranges and batches tag membership rather than querying each item. Note-reference indexes prevent permanent deletion from scanning linked tasks, bookmarks and attachments. Startup migrations build these indexes on existing data without rewriting content. Indexes trade additional disk space and write work for faster reads; pagination, relevance ordering, revisions and authorization remain unchanged.

Before changing a note's title or document, keep a checkpoint if the previous checkpoint is at least five minutes old. Restore uses a compare-and-swap revision check, forces a checkpoint of current content and rebuilds outgoing links in the same immediate transaction. Keep the newest 100 checkpoints and retain note-owned attachments.

Recurring completion reads the expected revision and creates one successor in the same transaction. Calendar arithmetic preserves a monthly anchor across short months and title-only edits. The browser supplies local calendar dates; task completion remains independent of the calendar reminder scheduler. Template instantiation copies encrypted attachments before committing the new document and remaps file IDs. Concurrent daily creation converges on the existing unique note and removes losing copies.

Lossless bundles use version four and accept versions one through three. Boards, archive state, task membership, stages and positions are preserved. Import remaps note/file/task IDs, history documents and internal links, validates recurrence relationships, and preserves conflicting daily content as regular notes. Encrypted full-instance recovery includes the new schema and selected daily-template setting without a separate backup format.

## Reader and application fallbacks

Publishing prepares HTML in a bounded worker before committing the encrypted publication snapshot and its HTML together. The public route reads that prepared HTML through an indexed token lookup, checks the current publication, and disables HTTP caching, so revocation is immediate. Existing snapshots are prepared at startup when missing or when the renderer changes. Reader scripts, styles and the rendering worker are built before development startup or production compilation; visiting a share link does not compile the React reader. The React reader escapes text, validates link and media schemes, and renders paragraphs, lists, tables, code and attachment previews into the initial HTML without loading the editing runtime. Syntax coloring and sanitized Mermaid SVG are lazy client enhancements; source code remains readable without JavaScript. Public pages carry a scoped CSP and expose only the snapshot's referenced token-scoped files. Editing the private original does not change the snapshot until republishing.

Application and shared-page CSPs use fresh script and stylesheet nonces, block inline style attributes, and restrict displayed images and media to same-origin files, generated data images and local blobs. Shared HTML stores a nonce placeholder; serving it replaces only nonce/meta attributes, preserving prebuilt publication behavior and generating a different nonce for every response. The browser retains the original document's nonce across client navigation and server-component refreshes. Reader colors and alignment become validated CSS classes in a nonce-bearing stylesheet. The offline PWA page uses a hashed stylesheet and a native reconnection form.

Cross-origin isolation uses `Cross-Origin-Embedder-Policy: require-corp`, with same-origin resource and opener policies. Linked HTTP(S) images, audio and video are served through an authenticated media endpoint; public shares can access only URLs referenced by their current snapshot. The relay uses the bookmark fetcher's public-address validation, pinned DNS and redirect checks, validates content by bytes, and rejects active HTML/SVG formats. It forwards no client credentials, permits two concurrent fetches and sixteen queued requests, and bounds each request to ten seconds and the configured upload limit. Upstream bodies are buffered within that limit before local range responses; this is a compatibility relay, not a streaming media cache.

Pinned editor and diagram dependencies receive narrowly scoped CSP compatibility patches during installation. Trusted programmatic styles use CSSOM, generated stylesheets receive the page nonce, and closing editor popovers avoid reinserting cached inline-style HTML. Package versions and exact source matches are checked before applying patches; upgrades require compatibility review rather than silently disabling the policy. Diagram output remains sanitized, and external CSS references are removed before display.

Theme initialization runs once in the server-owned document head before paint. The next-themes context still handles appearance changes and system preference updates; its redundant injected script is an inert text data block, avoiding React 19 client-remount warnings.

Unknown application routes and revoked share links return 404 pages. Workspace loading is scoped to its route group so a public missing note does not stream a successful loading response. Route and root error boundaries provide recovery controls without exposing exception details. Their retry action requests the page again rather than reusing a failed server-component response. Migration 0009 removes only the unchanged automatically seeded Journal default. New entries are blank unless a template was explicitly selected.

## Editor controls and shared media

Checklist blocks render with Nivra’s shared shadcn checkbox while preserving BlockNote’s keyboard shortcuts, parsing, canonical JSON, and Markdown checklist conversion. Native checkbox markup in exported HTML is a serialization format, not a visible app control. Existing Mermaid diagrams remain editable and exportable; Diagram is omitted from the creation menu, while Drawing remains available.

Editor and reader audio/video blocks share a client player with styled play/pause, seeking, volume, retry, and video fullscreen controls where the browser supports them. The reader still sends its prose and file links as initial HTML. A no-script link opens each media file when JavaScript is unavailable; interactive playback controls require JavaScript. The player synchronizes already-loaded metadata on attachment, so media loaded before hydration still shows its duration and permits seeking. Public media remains scoped to the published snapshot. Browser codec support determines which media formats can play.

## Paged tasks and bookmarks

`GET /api/v1/tasks` and `GET /api/v1/bookmarks` return `{ items, next }` pages of at most 100 rows (default 60) in a stable order; `next` is an opaque cursor for the following page, and `null` marks the end. Tasks are ordered newest-created first with an ID tie-breaker, and accept `filter` (`open`, `completed`) and `q`; bookmarks accept `q`, `favorite=1`, `collection`, and `unfiled=1`. `?summary=1` returns task open/completed counts or the bookmark total for the same filters plus the owner's collection names. Malformed cursors return 400. Bundle export and import read complete sets directly on the server. Access requires an owner session or a scoped API key.

## Chunked file encryption

New files use the chunked v2 format: a 28-byte header (magic, chunk size, random 16-byte salt) followed by 64 KiB plaintext chunks, each sealed with AES-256-GCM and followed by its 16-byte tag. A per-file key is derived with HKDF-SHA256 from the files key and the salt. Each chunk's nonce is its 32-bit index plus a final-chunk flag, and the object identifier is authenticated data on every chunk. Reordering, splicing chunks between objects or files, truncation, appended chunks, a wrong key, and any changed byte are rejected by authentication. Chunk offsets are computed from the stored size, so a range read fetches only the covering bytes: a file read for local storage, or `Range` requests for S3-compatible storage (a server that ignores `Range` and returns the whole object is handled). Plaintext is released only after the chunk containing it has authenticated; a damaged chunk therefore fails the request when that part is read. A response that has already started streaming cannot change its status, so it is aborted instead. Whole-object verification still happens when backups read every file.

Objects written in the earlier single-message v1 format remain readable. Because that format authenticates the whole file at once, such a file is decrypted in full for the request that opens it. When it is at least 1 MiB it is then converted in place to the chunked v2 format: the converted copy is verified against the original plaintext before the atomic replace, one conversion runs at a time, a failure leaves the original untouched, and deleting a file waits for its conversion so it cannot be recreated. Uploads are still read into memory before encryption (up to the System upload limit, at most 100 MiB), as are bundle export/import and the per-object step of backups; those paths are not streamed.

## Section switching

The workspace shows a section's rows only when they belong to that section. Each list records the section (view and tag; filter for tasks; favorites and collection for bookmarks) that its rows were loaded for, so a new heading is never drawn over the previous section's data. A small in-memory cache (`src/lib/section-cache.ts`) keeps the last-known first page, counts and Overview snapshot per section and shows them immediately on revisit while a fresh copy loads in the background; a section with nothing known shows a skeleton sized to its real rows. Only the section being visited loads its data; startup does not prefetch every collection or load hidden note lists. Overview refreshes on entry, focus, visibility, local actions and completion events rather than continuously polling. Its minute clock also refreshes data when the local calendar date changes. The shared SSE client retains its disconnected-stream fallback. The cache is memory-only, cleared on reload, sign-out, whenever the workspace unmounts, and on import, cleared for the affected section when something is captured, and cleared for other sections when a list is edited locally. Nothing is written to browser storage or the service worker, so private content is never cached persistently.

## Background jobs and live updates

File artifacts are acknowledged after validation and encrypted storage, with their SQLite row and extraction job committed in one transaction. Audio/video originals need no text job. Other files begin with `pending` extraction; supported documents become `done`, unsupported formats become `none`, and exhausted failures become `failed`. Pasted text remains immediate. Bookmark creation commits a saved URL and `pending` metadata job before fetching its preview. Refresh schedules the same job again.

The Node server starts two worker slots during instrumentation startup. Thumbnail jobs take priority so previews appear before longer recognition work. Otherwise, scheduling favors a bookmark slot alongside artifact extraction; either kind can use both slots when the other has no ready work. Jobs live in encrypted SQLite, with atomic claims, two-minute leases, thirty-second lease renewal, and three attempts. Failed attempts wait one then two seconds before retry. Expired leases recover after restart; a lease token fences late results from replaced workers. Deleted artifacts/bookmarks remove their job records. Completion writes and FTS triggers commit before an invalidation event becomes visible. Generated bookmark assets are discarded if the item was deleted or the lease was lost. Titles and descriptions explicitly edited by the owner survive preview refreshes; migrated bookmarks preserve their existing details.

Extraction runs in a separate Node worker thread with a 100-second deadline and a 512 MiB JavaScript heap limit. File size, text, PDF page and image pixel bounds remain enforced. This heap limit does not bound all native/ArrayBuffer memory. OCR uses bundled English language data; PDFs use embedded text. No media transcription is provided. The build/dev/test setup generates `generated/processing-worker.cjs`; production tracing includes it and the existing OCR/PDF dependencies.

A single authenticated `GET /api/v1/completions` stream per visible workspace sends small completion events containing an ID, kind, target ID and status. It sends no document, URL or extracted text. The server rechecks the SQLite session every second and closes revoked/expired sessions. Heartbeats run every fifteen seconds; disconnects release timers and listeners, and slow readers are disconnected instead of buffered indefinitely. The latest 1,000 events are retained in encrypted SQLite.

Every connection sends an explicit `resync` invalidation, including reconnections with `Last-Event-ID`; the client fetches current authorized data rather than depending on replay of a potentially truncated event log. Focus also reconciles, hidden tabs close their stream, and a thirty-second fallback reconciles while disconnected or when heartbeats stop arriving. Cards, open artifact viewers, active search results, Overview and backup status subscribe to the same stream. Tasks also reconcile on focus/reconnect when their edit dialog is closed. Section headings have no manual refresh action. Refreshes preserve editor drafts and revision conflict checks. Existing backup creation keeps its own lock/recovery behavior and emits a completion invalidation; it is not an extraction/metadata queue job.

The stream is private, uncached and marked `no-transform` and `X-Accel-Buffering: no`. Active streams close on SIGTERM/SIGINT so they do not hold production shutdown open; their timers and process listeners are released. The service worker excludes all API requests. Configure reverse proxies to flush streaming responses promptly, avoid response buffering and compression buffering, and allow idle connections beyond the heartbeat interval. Verify receipt through the actual proxy after deployment. Uploads and edits remain ordinary HTTP requests; SSE handles one-way completion updates.

Queue limits apply per Node process. Nivra supports a compact single-instance deployment; SQLite lease fencing also prevents two processes from committing the same job, but multiple independently launched app processes each have their own two-slot concurrency limit. A restart may leave an unfinished job waiting up to two minutes for its lease to expire. Pending jobs are preserved by encrypted instance backups and pending bookmarks are requeued during bundle import.

Artifact thumbnail jobs have their own durable queue kind and emit artifact completion invalidations. Upload and startup backfill schedule supported media previews; deletion cancels both recognition and thumbnail jobs. Preview writes are fenced by the job lease, and abandoned generated files are discarded. The build includes `generated/thumbnail-worker.cjs`, Sharp, unpdf and the native Canvas renderer. Docker supplies FFmpeg and local fonts; source deployments need FFmpeg on PATH for video previews. Without a supported decoder, the original remains available with a file-type icon. Preview generation has a 25-second deadline and a 256 MiB JavaScript heap limit; native memory is separate.

## Private artifact shelf

Migration 0014 adds owner-scoped artifacts and FTS5 indexes. SQLite stores titles, filenames, extracted text, dimensions, extraction state and revisions; originals and thumbnails use the encrypted local/S3 file adapter. Artifact search participates in global full-text and fuzzy search. Uploads preserve originals, while two worker slots claim durable SQLite jobs for bundled English OCR or bounded PDF extraction, recovering expired leases after restart. Text and metadata mutations require the current revision. Private file responses retain authenticated range delivery. Full-instance backups enumerate both original and thumbnail keys and validate artifact search indexes during recovery. Note bundles retain their existing scope. Extraction is bounded to 200,000 characters; embedded PDF text supports up to 400 pages and 40 MiB. OCR supports images up to 60 million pixels with a 90-second deadline.

## Storage identity

Configuration and application URLs use `NIVRA_*` and `/api/v1/`. The database filename is `nivra.sqlite`. Cryptographic signatures and key derivation remain fixed to preserve encrypted objects.

## Calendar

Owner-filtered calendar APIs store events, linked content, recurrence exceptions, tags and date-only task plans in SQLite. Range queries use dated indexes and bounded recurrence expansion; responses include exact daily counts and pagination. An in-memory range cache invalidates on SQLite connection changes and does not persist private content in the browser. Global search indexes event titles and descriptions in FTS5. Event edits enforce revisions, and agents can move events to Trash but cannot restore or permanently delete them.

The reminder worker runs in a separate bounded lane from media processing. SQLite deduplicates occurrences and stores per-device leased deliveries, retry deadlines and missed reminders. Each delivery rechecks the source revision, active state and authenticated device session. Push endpoints must resolve to public HTTPS addresses; requests use pinned DNS, deadlines and encrypted subscription storage. Device subscriptions and generated VAPID keys are installation state, excluded from portable exports.

Reminder identity uses the source, occurrence and scheduled time rather than its content revision. Edits refresh queued metadata while preserving accepted device deliveries and pending retries. Delivery checks also suppress repeats from older revision-based queues.

## System configuration

First-run health/status do not initialize SQLite. Account setup commits the installation encryption choice and canonical origin before database creation. Mutable storage, upload and backup settings are revisioned in SQLite; S3 connection profiles are separately encrypted with the master key in both content-encryption modes. Docker exposes only port, public origin and an optional external key file.

File operations pin a storage profile through completion. Destination changes verify S3 permissions, wait for active writes and switch new writes atomically. Durable per-file locations retain reads from earlier profiles until a resumable, verified transfer commits each new location. Source copies remain retained. Backup archives retain their original repository profile; recovery restores files into local storage and rebases the installation profile when its data volume is mounted at a different path. Settings changes and transfer progress use the existing authenticated completion stream.

Workspace section routes validate installation and owner sessions before rendering, outside a streamed loading boundary so404 is sent before response headers. A fresh installation serves onboarding only at the root; unknown paths and missing authenticated note/task/board/event/tag targets return404. Signed-out requests to known sections return to root login without probing private item existence. Public shares return a styled404 for missing/revoked links or503 with Retry-After for temporarily unavailable pages; neither response discloses private content or initializes a fresh installation.

## Forms and submissions

`forms.ts`, `form-results.ts`, `form-uploads.ts` and `form-trash.ts` are shared application services. Thin HTTP/MCP adapters use the same strict schemas and owner/scoped access boundaries. Forms use created-time keyset cursors with explicit next cursors and exact counts; indexed answer search is bounded. Responses reference immutable published versions. Submission retries bind a stable key to validated answers/files and atomically recheck version/status before attaching files.

Anonymous upload sessions use hashed secrets bound to one form/version, 24-hour expiry, byte/count/budget reservations before body reads, one-writer claims, signature validation and generated storage keys. Retained files and thumbnails follow local/S3 encryption and authenticated serving. The existing durable job worker generates supported thumbnails; cleanup removes expired temporary uploads. Full backups inventory durable files/thumbnails and preserve publication, historical definitions, results and indexes. Form restoration revokes publication; response restoration requires an active parent. Agent credentials can read responses and move active content to Trash, with restoration/purge remaining owner-only.

`/api/v1/forms` operations and public submission/upload routes are described in the repository OpenAPI contract. Private file/export results return canonical URLs; MCP credentials use `/mcp/files/form-file/...` and `/mcp/files/form-export/...`. OAuth remains limited to MCP. SSE invalidates Forms lists and reconciles active forms/results without replacing unsaved drafts.

Form deadlines persist a local date, timezone and exclusive next-midnight timestamp. Public reads, submissions and upload reservations enforce expiry without a polling job. Calendar derives deadlines and indexed daily submission aggregates from active forms/responses, so edits, revocation and Trash need no duplicate calendar events. Submission lists/exports accept `date` and `timezone` filters. Forms JSON mutations also support idempotency keys for save retries.

## Smart tagging and search

Migration 0045 records optional post-setup onboarding progress on the instance. Existing installations default to `complete`; new password/passkey owners begin at `tags`. Added tags appear in a separate “Your tags” list above suggestions; owners can also create their own. A compact, default-off “Enable smart features” option is available during tag setup; progression waits for its persisted update. Device installation guidance retains a supported browser install event until explicitly requested, handles standalone launches and iOS Safari instructions, and remains skippable. Desktop guidance introduces the actual Search, Quick and New note shortcuts.

Source builds include opt-in, English local AI, disabled by default. Settings → System labels these capabilities “Smart tagging and search” and keeps the enable switch, coverage and retry controls. The private `/tag-suggestions` workspace page is reached from Tags or a tagged collection. Tags can have up to ten optional matching words/phrases. Existing-tag suggestions show a bounded source excerpt; clicking a card opens the original item. Add tag merges into current assignments with revision checks; the labeled top-right dismiss control preserves rejection history without assigning a tag. Neither existing-tag review action creates tag names. Successful reviews update the cards without a visible success banner; screen readers receive a brief status announcement. Completion events coalesce behind in-flight requests, and decision generations fence older responses. Proposals remain outside content DTOs, public pages, ordinary exports and agent tools. Form responses support private manual tags and appear in their owner's tagged collection.

Overview displays open tasks, upcoming events, recent content and owner-only review information in separate cards. Section descriptors declare visibility and compact or roomy sizing; a shared responsive layout groups compact cards and gives longer lists their own space. Future sections use the same structure rather than nesting inside another card. Existing API fields remain available; browser requests supply the device timezone for calendar expansion. Review counts contain no response text, suggestions or vectors and are omitted for agent credentials. Normal content and indexing completions refresh the dashboard through SSE while retaining the current cards during background loading.

One pinned Arctic Embed XS q8 model serves both suggestions and semantic search. When smart features are enabled in onboarding or System settings, the workspace automatically uses semantic retrieval for nonempty queries; empty queries show recent items, and unavailable inference falls back to keyword search. There is no per-query switch. `ai/model-manifest.json` pins revision, artifact hashes, query prefix, CLS pooling and normalized 384-dimensional text vectors. The Debian Bookworm Slim image bundles assets, tokenizer and CPU-only ONNX Runtime Node. Runtime downloads are prohibited. Visual models and generative tag naming remain deferred; model/version/modality/dimension metadata isolates future embedding spaces.

Migration 0046 adds adaptive matching, encrypted tag-label/example caches, automatic-assignment provenance and bounded reusable-topic proposals. Existing tag names/aliases and owner-confirmed canonical examples are ranked before unmatched-topic extraction. Unapproved automatic assignments are excluded from examples. Per-tag revisions and an installation matching epoch fence stale results; a coalesced durable refresh reuses existing content vectors. Revision changes immediately clear learned example profiles, including when no indexing jobs remain; label/model refreshes also discard old profiles before rebuilding. Review suggestions remains the default. Automatic tagging is an explicit owner setting and uses stronger evidence gates. Owner rejection suppresses alternate guesses for that source fingerprint. Content-generation changes remove stale unapproved automatic memberships only when no other fresh source supports them; approved/manual assignments remain.

New-tag ideas use extracted phrases from at least three distinct, current, untagged items, rather than a generative model. Before proposal admission, invalid evidence is removed and pending proposals with no current evidence are retired; proposals with one or two current examples remain hidden while they collect more evidence. Proposal history and daily automatic creation are bounded. Existing names and aliases are reused before creation. Owner corrections for the current source fingerprint, including rejected decisions left by deleted tags, remain until the source changes or is deleted. Only obsolete-fingerprint decisions are pruned after 180 days and capped at 128 per source; current-fingerprint corrections are intentionally uncapped to preserve arbitrary owner vocabularies. Only reviewed form responses can contribute learning examples or autonomous writes; authorized owner search continues to include private unreviewed responses. Private proposals and provenance are excluded from public content, ordinary content DTOs, portable exports and agent administration. Automatic mode and adaptive matching require representative owner-vocabulary review before release; small synthetic checks are regression evidence rather than a universal accuracy guarantee.

Migrations 0043/0044 add private indexing, extraction, chunk, suggestion, decision and response-tag tables plus semantic jobs. SQLite triggers atomically dirty generations during canonical mutations, imports, duplication, OCR completion, parent visibility changes and Trash operations. Generation changes immediately remove stale chunks/proposals. Permanent deletion cascades derived records. Background work reads canonical sources, extracts supported attachment text, runs bounded 160-word chunks outside SQLite transactions/storage guards, and commits only with current owner, visibility, generation, fingerprint, vocabulary and job lease. Vocabulary-only refreshes reuse text vectors. Private vectors stay within the configured SQLite encryption boundary; full-instance recovery includes them, while portable exports include only canonical content and manual tag metadata.

The build traces the CommonJS indexing worker separately and verifies its dependency closure in the standalone artifact. A persistent child process owns the model and a private, bounded vector cache. An OS lock elects one model worker per data directory; other processes retain keyword fallback and cannot claim its inference jobs. Another installation-wide OS lock serializes OCR, model initialization and inference even across lease expiry. Jobs keep heartbeats, bounded retries, abort signals and fenced commits. Indexing has 32 durable queued/running jobs and an eight-operation local queue; no content save waits for inference. Public-response and response-file indexing share a durable installation-wide cooldown: processing time is followed by nine times that duration (at least one second between starts), and a crashed reservation conservatively defers that work for 30 minutes. Waiting sources stay pending; owner-created content and keyword search remain available. AI completion events update AI controls independently from content-section refreshes.

The worker targets 512 MiB RSS, including a 192 MiB estimated vector-cache budget. Scans stop at 448 MiB to leave room for transient allocations. Heap, source/file limits, deadlines, RSS monitoring and child termination provide graceful failure; this RSS target is not an operating-system reservation. Index capacity is 100,000 text chunks, rather than a promised content-item count. Excess work stays explicitly pending/capacity-limited, with coverage shown and lexical search retained. Memory/deadline failure never returns a partial dense scan as complete. Cold encrypted scans can exceed that budget and return keyword fallback; a bounded packed cache keeps completed scan prefixes for later queries. A 3-second query budget includes worker queueing; scans run in bounded pages in the child, never in HTTP handlers. Native performance at larger scale must be measured rather than inferred from small quality fixtures.

Default keyword/recency search and exact counts retain their behavior. `/api/v1/search?strategy=semantic` and MCP `search` opt in to bounded related matches. Protected hybrid ranking uses alpha 0.5, FTS candidate union and literal protection for quoted phrases, filenames, identifiers, error codes and ISO dates. Results are canonical items (including owner-only form responses), deduplicated by item and rechecked for active visibility after retrieval. Raw vectors and cosine scores are not returned. `strategyUsed` reports semantic retrieval or keyword fallback; semantic `total` counts the bounded candidate set (at most 30), not every potentially related item. Related matches are suggestions, never generated answers or proof that requested information exists.

`/api/v1/ai` and suggestion review require the owner browser session and origin checks; API keys/OAuth cannot administer these operations. Review requests are safe to retry after an interrupted response. Integrated security, backup/restore, lifecycle, native architecture, resource and responsive UI checks—and representative human owner-vocabulary review—remain release gates for this feature branch.
